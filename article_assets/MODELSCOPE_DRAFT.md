# 【性能测试】Qwen3.8-27B 长 Prompt 缓存值不值得用？60 次真实调用实测命中、延迟与 Token 成本

> 本文包含 6 次 pilot 预检和 54 次正式调用。所有请求均真实调用阿里云百炼华北 2（北京）的 `qwen3.8-27b` 模型；原始逐条记录、预注册设计、固定随机执行顺序、确定性评分器、分析脚本及 SHA-256 校验清单已全部开源：  
> GitHub 仓库：https://github.com/Sam-Hui-dot/qwen38-context-cache-benchmark

---

## 一、先给结论：显式缓存复用覆盖率 99.2%，综合输入成本节省 51.4%

在本实验的连续三次请求链中，**显式缓存（Explicit Cache）表现出高度的确定性与稳定性**：6/6 条链均呈现“首请求创建、后两次稳定命中”，复用请求命中率为 12/12（100%），缓存 Token 覆盖率达到 **98.49% ~ 99.70%（平均 99.2%）**。按百炼官方价格权重折算，三次请求链的总等价输入成本约为匹配冷请求的 **48.6%**（中位净节省 **51.4%**）。在端到端响应耗时上，显式三请求链观察到的链总延迟中位数下降为 **41.0%**。

**隐式缓存（Implicit Cache）无需客户端改造，但行为具有不确定性**。更重要的是，本次严密的随机执行顺序暴露了关键的实验设计问题：不仅存在显式请求对后续隐式请求的预热残留，反方向上也观察到了隐式请求缩短显式首发创建延迟的迹象。本文完整保留全部 54 条原始数据，将“排除串扰后的 4 条隐式链”单独作为事后（post-hoc）敏感性分析呈现；同时将 41.0% 延迟降幅明确界定为描述性观测结果，而非严格隔离下的纯因果估计。

## 二、结果速览表：三类策略全景横评

| 策略条件 | 缓存生效行为 | 3次请求等价输入成本 | 链总响应延迟 | 应如何客观解读 |
|---|---|---:|---:|---|
| **冷请求基线 (Cold Control)** | 18 次请求 `cached_tokens` 恒为 0 | 100% (基线) | 总体中位 1,885.1 ms | 严格阻断公共前缀的对标对照组 |
| **显式缓存 (Explicit Cache)** | 6/6 条链首发创建、后续稳定复用 | **链中位节省 51.4%** | **链中位下降 41.0%** | **本实验中最稳定、工程落地最可控的策略** |
| **隐式缓存 (全量 6 条链)** | 2 条链首发即命中（受此前显式链预热） | 链中位节省 41.9% | 链中位下降 38.1% | 受执行顺序与残留状态影响，不宜作无偏估计 |

*注：等价输入成本依据阿里云百炼官方公开单价与 API 返回的 `prompt_tokens`、`cache_creation_input_tokens`、`cached_tokens` 严格折算，输出 Token 均单独全额计费。*

## 三、为什么测这个？长 Prompt 时代的四大工程现实问题

在 Agent 智能体、企业知识库（RAG）、多轮代码调试等场景中，开发者往往需要反复发送超长上下文——包括庞大的人设指令、API Schema 定义、企业规章或长代码文件。工程选型上面临四个具体疑问：

1. **隐式缓存是否稳定？** 不写额外参数让系统自动识别前缀，在多轮调用中命中率多高？
2. **显式缓存首次创建多收 25% 溢价，到底复用几次能回本？** 若会话轮数较短，会不会反而更贵？
3. **缓存省下的究竟是逻辑 Token、实际费用，还是响应延迟？** 延迟下降幅度是否与 Token 比例对齐？
4. **启用缓存后，模型输出是否会因 KV 状态复用而产生漂移或质量退化？**

为了给出有数据依据的工程参考，我围绕百炼平台托管的 `qwen3.8-27b` 设计了受控基准测试。

## 四、百炼 Context Cache 官方机制与计费规则

根据百炼官方文档，`qwen3.8-27b`（华北 2 / 北京）原生支持上下文缓存。底层计费机制如下：

- **冷请求普通输入**：按标准单价 $100\%$ 计费（当前刊例价 ¥3/M tokens）；
- **隐式缓存**：自动识别公共前缀（需 $\ge 1024$ tokens），命中部分按标准单价 **$20\%$** 计费（省 80%），但官方明确指出其生命周期由系统动态管理，存活时间具有不确定性；
- **显式缓存**：通过 `"cache_control": {"type": "ephemeral"}` 声明边界。**创建时按标准单价 $125\%$ 计费（收 25% 溢价）；在 5 分钟有效期（TTL）内，命中 Token 仅按标准单价 $10\%$ 计费（省 90%）**，命中会自动顺延 5 分钟；
- **输出 Token**：始终按全额价格（¥12/M tokens）独立计费。

显式缓存本质是一笔“前期溢价创建、后续深度折扣”的经济账。

## 五、实验设计与控制变量：三策略 × 三档位 × 双样本

实验固定使用百炼 `qwen3.8-27b`，关闭思考模式（`enable_thinking=false`），`temperature=0`，`max_tokens=128`，超时 90 秒，严格单流串行，**关闭自动重试（每 observation 仅 1 次 HTTP 请求）**。

实验矩阵设计：
- **3 种策略**：
  - `A: Cold Control（冷请求基线）`：Prompt 最前侧注入每次唯一的动态随机 Nonce，强制全量 Prefill 计算；
  - `B: Implicit（隐式缓存）`：不传缓存参数，长前缀文本完全一致，测试云端自适应识别；
  - `C: Explicit（显式缓存）`：长前缀文本与 B 严格一致，文档尾部声明 `cache_control: {"type": "ephemeral"}`。
- **3 个 Prompt 档位**：`L1 (~2K tokens)`、`L2 (~6K tokens)`、`L3 (~10K tokens)`。
- **2 套独立合成台账样本**：`doc1` 与 `doc2`，完全由程序合成的虚构数据，排除互联网污染。
- **每条缓存链连续 3 次请求**：`pos=1`（首发创建/冷启动）、`pos=2`（首次复用）、`pos=3`（二次复用）。

总 observation 计算：$3 \text{ 策略} \times 3 \text{ 长度} \times 2 \text{ 样本} \times 3 \text{ 请求} = \mathbf{54 \text{ 次正式调用}}$。18 条链以 `seed=20260906` 完全随机排序，链内 3 次请求保持连续执行。

## 六、确定性机器评分体系：告别 LLM-as-judge，只看绝对真值

为避免评分模糊或 LLM-as-judge 漂移，每道题均为确定性台账字段检索，强制模型返回单行 JSON：
```json
{"answer": "<精确目标值>", "evidence_id": "<唯一记录ID>"}
```
评分程序通过本地 Python 函数严格比对 Ground Truth 字符串和关联证据编号。54 次正式请求中，**机器验收通过率为 54/54（100%）**。这表明：**在本实验测试的确定性抽取任务中，未观察到由缓存引起的准确率下降**，但不外推为所有复杂生成任务通用无损。

## 七、Smoke 门禁与真实校准：在调用前修正 Prompt 规模

正式运行前按规范执行了 6 次 live smoke 预检，有效拦截了偏差：
最初按字符估算的文档偏大，百炼返回的实际 `prompt_tokens` 达 3,163、9,409 和 15,654 tokens，超出原定区间。我原样保留这 6 次超出区间的 smoke 记录，利用实测斜率将记录数校准为 24/79/133，建立 `PREREGISTRATION_V2.0_AMENDMENT.md` 重新冻结并生成清单，再开启正式调用。校准后各档中位数分别为：**L1=1,986、L2=6,025.5、L3=9,987.5 tokens**。

## 八、结果一：显式缓存的复用覆盖率与稳定性实测

![缓存覆盖率](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig01_cache_coverage_cn.png)

实测数据表明：
- **显式缓存（Explicit）6 条链规律明确**：首个请求（pos=1）`cached_tokens` 均为 0 并返回 `cache_creation_input_tokens`；pos=2 和 pos=3 全部命中（Hit Rate 100%）。
- 在 L1、L2、L3 三档下，复用请求的 `cached_tokens` 实际命中范围分别为 **1,956 ~ 1,959**、**5,995 ~ 5,999** 和 **9,951 ~ 9,968** tokens，**缓存 Token 覆盖率稳定在 98.49% ~ 99.70%（平均 99.2%）**。
- **冷请求基线（Cold Control）**：18 次请求 `cached_tokens` 均为 0，证明前置动态 Nonce 阻断前缀有效。

## 九、结果二：延迟阶梯实测——从 3.0 秒到 0.8 秒的加速表现

![响应延迟](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig02_latency_cn.png)

*注：图中展示各策略在相应长度档位下纳入请求的中位延迟，其中隐式缓存仅统计无串扰子集；下表进一步按链内位置使用均值拆解显式缓存的创建与复用延迟。*

| Prompt 规模 | 冷请求平均延迟 | 显式第 1 次 (创建缓存) | 显式第 2 次 (首次命中) | 显式第 3 次 (二次命中) | 复用请求平均降幅 (vs 冷请求) |
|---|---:|---:|---:|---:|---:|
| **L1 (~2K tokens)** | 1,110.6 ms | 843.0 ms | 780.8 ms | 771.3 ms | **下降 30.1%** |
| **L2 (~6K tokens)** | 1,920.5 ms | 1,412.3 ms | 733.2 ms | 775.9 ms | **下降 60.7%** |
| **L3 (~10K tokens)** | 2,974.6 ms | 1,978.9 ms | 972.9 ms | 836.8 ms | **下降 69.6%** |

核心观察：
1. **长前缀下复用请求提速明显**：在 10K 档位下，冷请求平均耗时近 3 秒（2,974.6 ms），而命中缓存后回落至 **1 秒以内（836.8 ~ 972.9 ms）**，复用请求平均延迟降幅近 70%；
2. **延迟指标应作描述性理解**：本次执行顺序下显式三请求链观察到的总延迟中位下降为 41.0%。但排查发现部分匹配隐式链先于显式链执行，该延迟指标可能受跨条件预热影响，建议视为描述性统计而非严格纯因果估计；
3. **长尾与排队波动仍在**：云端多租户环境下，缓存主要优化 Prefill 计算开销，不消除网络与排队波动。

## 十、结果三：成本模型与 ROI 推导——到底复用几次才真正回本？

![等价输入成本](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig03_cost_cn.png)

显式缓存虽然有单价 10% 的深度折扣，但首次创建需付 25% 溢价。设稳定前缀长度为 $L$，普通输入基础单价为 $P$：
- **不使用缓存，调用 $N$ 次累计成本**：$C_{\text{cold}}(N) = N \cdot L \cdot P$
- **使用显式缓存（第 1 次 125%，后 $N-1$ 次 10%）累计成本**：$C_{\text{explicit}}(N) = [1.25 + 0.10(N - 1)] L P = (1.15 + 0.10 N) L P$
- **盈亏平衡点**：$1.15 + 0.10 N \le N \implies 0.90 N \ge 1.15 \implies \mathbf{N \ge 1.278}$

**ROI 推演结论**：
1. **$N=1$（单次调用）**：成本为冷请求的 $1.25$ 倍，**净亏 25%**（单次场景坚决不加显式缓存）；
2. **$N=2$（仅需复用 1 次）**：显式成本 $1.35LP$ vs 冷请求 $2.0LP$，**即可净省 32.5%**；
3. **$N=3$（复用 2 次，本实验场景）**：显式成本 $1.45LP$ vs 冷请求 $3.0LP$，理论节省 **51.7%** —— 与 54 次实测得到的 **51.4% 中位净节省** 高度一致；
4. **$N=10$（长期复用）**：显式成本 $2.15LP$ vs 冷请求 $10.0LP$，**净省 78.5%**，逼近 90% 的理论极限。

## 十一、深度排障复盘：还原 L2-d2 与 L3-d2 隐式缓存被意外预热的时间线

![执行顺序审计](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig04_execution_heatmap_cn.png)

本次实验最值得公开复盘的现场是**隐式缓存出现的两次“异常提早命中”**：
- `execution_index=49` (implicit, L2, doc2, pos=1)：首发请求返回 `cached_tokens = 4992`；
- `execution_index=52` (implicit, L3, doc2, pos=1)：首发请求返回 `cached_tokens = 8320`。

精确时间戳日志还原现场：
```text
[05:40:36 UTC] index=34: explicit, L2, doc2 (pos=1) -> 创建 L2-doc2 显式缓存
[05:40:39 UTC] index=36: explicit, L2, doc2 (pos=3) -> 完成显式链调用
... 仅相隔 12 秒 ...
[05:40:51 UTC] index=49: implicit, L2, doc2 (pos=1) -> 发起首个隐式请求，命中 4992 tokens！

[05:39:49 UTC] index=4: explicit, L3, doc2 (pos=1) -> 创建 L3-doc2 显式缓存
... 相隔 64 秒 ...
[05:40:53 UTC] index=52: implicit, L3, doc2 (pos=1) -> 发起首个隐式请求，命中 8320 tokens！
```

与此同时，反向关系同样存在：L3-doc1 与 L2-doc1 均是 implicit 链先于 explicit 链执行；随后显式首次创建耗时分别仅 **846 ms** 和 **770 ms**，明显低于各自匹配冷链首发的约 **2.77 s**（`2772.9 ms`）和 **2.16 s**（`2164.5 ms`），提示其延迟可能受到前置请求预热影响。

**客观推断与工程警示**：  
这一现象与跨条件缓存状态残留的解释高度一致，但现有实验数据无法进一步判断显式缓存与隐式缓存是否共享底层存储架构，也不能据此推断百炼内部的具体实现机制。开发者若在测试环境做缓存对比，**单纯打乱请求顺序是不够的**，跨条件共用前缀必须注入独立命名空间或留出充分冷却时间。

## 十二、敏感性分析：排除串扰后的无污染子集表现

我们坚持预注册原则，未删改任何数据，全部 54 条调用原样归档。

事后（post-hoc）敏感性切片：剥离受影响的 2 条隐式链，仅对 **4 条严格无污染的隐式链**（首请求 cached=0，后两次自动命中）进行测算：
- **全量 6 条隐式链指标中位数**：等价输入成本中位节省 **41.9%**，链总延迟中位下降 **38.1%**；
- **无串扰 4 条隐式链指标中位数**：等价输入成本中位节省 **30.0%**，链总延迟中位下降 **31.7%**。

对比可见：排除残留预热后，隐式缓存仍可在免客户端改造下节约约 $30\%$ 的成本与延迟；但因单价折扣为 20%（显式为 10%），其综合降本幅度显著低于显式缓存的 51.4%。

## 十三、开发者工程落地指南：生产中如何设计 Prompt 布局与缓存边界

结合本次实测与官方规范，总结三条落地建议：

1. **三段式 Prompt 布局与显式边界划分**：
   - **头部固定区（系统人设、格式规范，>1K tokens）** $\to$ 结尾配置 `cache_control`；
   - **中部半稳定区（引用的文档、代码片段、上下文知识库）** $\to$ 结尾配置第 2 个 `cache_control`；
   - **尾部动态区（用户即时 Query、变动对话历史）** $\to$ 不设缓存标记。
2. **依据交互轮数决定是否开启显式标记**：
   - 评估业务场景：**若预计同一可缓存前缀会在显式 TTL 内至少命中复用 1 次（$N \ge 2$），从理论输入成本看即开始净省**，建议配置显式标记锁定 90% 深度折扣；单轮任务（$N=1$）坚决不加，避免 25% 溢价。
3. **正确理解 TTL 机制与测试隔离**：
   - 百炼文档明确指出，**显式缓存**具备 5 分钟基础有效期（命中顺延），而**隐式缓存**生命周期由系统动态维护，具有不确定性。做系统压测或多租户设计时，防范穿透最稳妥的手段是加入独立租户前缀。

## 十四、局限性说明与完整复现指引

明确本实验的边界条件：
1. **样本多样性**：采用 2 套完全合成台账文本，未覆盖复杂代码库或多模态语料；
2. **样本规模**：正式实验为 54 次调用（18 条缓存链），旨在提供工程机制对照与可复现基准，不作全域宏观统计外推；
3. **延迟指标描述性**：延迟数据反映评测时段内华北 2 地域公有云表现，部分链延迟受跨条件预热影响，应作描述性观测参考；
4. **成本基于公开计费模型折算**：金额为理论等价折算，实际支出视账户具体优惠与免费额度而定。
