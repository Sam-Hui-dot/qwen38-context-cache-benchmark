# 【性能测试】Qwen3.8-27B 长 Prompt 缓存值不值得用？60 次真实调用实测命中、延迟与 Token 成本

> 本文包含 6 次 pilot 和 54 次正式调用。所有请求均真实调用阿里云百炼华北 2 的 `qwen3.8-27b`；原始记录、固定执行顺序、预注册、确定性评分器和 SHA-256 均随复现仓库公开。

## 先给结论

在本实验的三次连续请求链中，显式缓存表现最稳定：6/6 条链均是首请求创建、后两次命中，复用请求缓存覆盖率约 99.2%。按官方价格权重折算，三次请求合计输入成本约为匹配冷请求的 48.6%，链总延迟中位减少 41.0%。

隐式缓存无需配置，但行为更不确定。更重要的是，本次随机执行顺序暴露了一个实验设计问题：两条隐式链在首请求就已命中，而且此前恰好运行过相同文本的显式链。它们可能受到 TTL 内缓存状态串扰。因此本文保留全部数据，同时把“无串扰的 4 条隐式链”只作为 post-hoc 敏感性分析，不能冒充预注册主结果。

## 为什么测这个

长系统提示词、代码库、合同或知识库材料经常会被重复发送。缓存听起来一定省钱，但工程上至少有四个问题：

1. 隐式缓存到底能命中多少？
2. 显式缓存第一次创建多收 25%，复用几次才回本？
3. 节省的是逻辑 Token、计费成本，还是响应延迟？
4. 缓存后模型答案是否仍然正确？

## 实验设计

我生成了两份完全合成的业务台账，在约 2K、6K、10K 三个服务端实测 Prompt 档位下，分别执行：

- 冷请求基线：最前方 nonce 每次变化，阻断公共长前缀；
- 隐式缓存：不设置缓存参数，链内前缀完全一致；
- 显式缓存：文本与隐式条件一致，在文档末端添加 `cache_control`。

每条链连续提出三个确定性检索问题，严格要求单行 JSON：

```json
{"answer":"<value>","evidence_id":"<record id>"}
```

评分器只接受精确 Gold 和证据记录，不使用 LLM Judge。正式设计为 `3×3×2×3=54` 个 observation；18 条链使用 seed `20260906` 随机排序，链内请求保持连续。Thinking 关闭，temperature=0，max_tokens=128，90 秒超时，不并发、不自动重试。

## Pilot 确实改变了设计，但发生在正式实验前

最初离线估算的文本过长。6 次 pilot 实测为 3,163 / 9,409 / 15,654 Token，超出冻结区间，所以 v1 smoke gate 被保留为失败，没有假装通过。随后只依据服务端 `prompt_tokens` 做线性校准，把记录数从 40/125/210 调整到 24/79/133，建立 v2.0 amendment，再冻结正式实验。正式数据实际中位为 1,986 / 6,025.5 / 9,987.5 Token。

## 结果一：显式缓存的复用覆盖率接近完整前缀

![缓存覆盖率](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig01_cache_coverage_cn.png)

显式缓存六条链的首请求均报告缓存创建，第二、第三请求均命中。复用请求平均缓存覆盖率约 99.2%。冷请求 18 个 observation 的 `cached_tokens` 全部为 0。

## 结果二：延迟下降，但服务负载仍是噪声

![响应延迟](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig02_latency_cn.png)

冷请求总体中位延迟为 1,885.1 ms，显式缓存为 813.7 ms。按每条三请求链与相同文档、长度的冷请求配对，显式缓存链总延迟中位减少 41.0%。P95 并没有同幅下降，说明网络和服务端负载仍然会制造长尾；本文不把缓存描述成确定性的延迟保证。

## 结果三：一次创建、两次复用时，显式缓存约节省一半输入成本

![等价输入成本](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig03_cost_cn.png)

采用实验日官方公开价格：普通输入 100%、隐式命中 20%、显式创建 125%、显式命中 10%。输出 Token 单独按原价计算，不享受缓存折扣。

在三次请求链中，显式缓存的等价输入成本中位为匹配冷请求的 48.6%，即中位节省 51.4%。理论上，如果稳定前缀占输入主体，一次创建后只要至少复用一次，`1.25 + 0.10 < 1 + 1`，便可覆盖创建溢价；只有一次请求则反而贵 25%。

## 一个必须公开的实验问题：两条隐式链可能被显式链预热

![执行顺序审计](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig04_execution_heatmap_cn.png)

L2-d2 和 L3-d2 两条隐式链在第一次请求就分别命中 4,992 和 8,320 Token；它们对应的显式链此前已经运行，而且整个实验未超过五分钟 TTL。因为两种条件文本相同、没有 washout，这两条链不能当成干净的“隐式首次请求”。

我没有删除、补跑或重排数据。全量预注册汇总原样保留；另做的无串扰敏感性分析只剩 4/6 条隐式链，其三请求链等价输入成本中位减少 30.0%，延迟中位减少 31.7%。这不是新的主结论，也不能证明两类缓存一定共享底层缓存，只能说明生产和实验都应关注跨请求的缓存状态。

## 实用建议

- 单次长请求：不要为无法复用的内容付显式创建溢价。
- 稳定前缀会连续复用至少一次：显式缓存更容易获得可验证、接近完整前缀的命中。
- 追求零配置：隐式缓存可以省成本，但要接受命中不保证，并真实记录 `cached_tokens`。
- 做性能评测：不同条件必须使用独立 cache namespace 或等待 TTL washout；随机顺序本身不足以消除缓存 carryover。
- 成本核算：`prompt_tokens` 是逻辑输入量，不等于最终计费量；必须区分普通输入、缓存创建和缓存命中。

## 局限

- 只有两份合成文档和三种长度，不代表所有真实业务文本。
- 正式实验只有 54 个 observation，重点是工程可复现，不是总体统计推断。
- 隐式条件有两条链存在顺序污染，可用证据弱于显式条件。
- 延迟仅代表实验时段、地域和服务状态。
- 费用根据公开单价和 usage 字段估算，不等于账单实扣。
