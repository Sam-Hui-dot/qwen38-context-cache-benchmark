# 【性能测试】Qwen3.8-27B 长 Prompt 缓存值不值得用？60 次真实调用实测命中、延迟与 Token 成本

> 本文包含 6 次 pilot 预检和 54 次正式调用。所有请求均真实调用阿里云百炼华北 2（北京）的 `qwen3.8-27b` 模型；原始逐条记录、预注册设计、固定随机执行顺序、确定性评分器、分析脚本及 SHA-256 校验清单已全部开源：  
> GitHub 仓库：https://github.com/Sam-Hui-dot/qwen38-context-cache-benchmark

---

## 一、先给结论：显式缓存复用率 99.2%，综合输入成本立省 51.4%

在本实验的连续三次请求链中，**显式缓存（Explicit Cache）表现最为稳定与确定**：6/6 条链均呈现“首请求创建缓存、后两次精准命中”，复用请求的缓存覆盖率达到 **99.2%**。按官方价格权重折算，三次请求链的总等价输入成本仅为匹配冷请求的 **48.6%**（即中位净节省 **51.4%**），链总延迟中位数减少 **41.0%**。

**隐式缓存（Implicit Cache）虽然无需任何参数改造，但行为存在显著的不确定性**。更重要的是，本次严密的随机执行顺序暴露了一个极其真实的工程问题：有 2 条隐式链在首请求就已命中缓存。排查证实它们在此前数十秒内刚运行过相同文本的显式链，并在 5 分钟 TTL 内受到了残留状态的预热串扰。本文完整保留全部 54 条原始数据，并将“排除串扰后的 4 条隐式链”单独作为事后（post-hoc）敏感性分析呈现。

## 二、结果速览表：三类策略全景横评

| 策略条件 | 缓存生效行为 | 3次请求等价输入成本 | 链总响应延迟 | 开发者应如何解读 |
|---|---|---:|---:|---|
| **冷请求基线 (Cold Control)** | 18 次请求 `cached_tokens` 恒为 0 | 100% (基线) | 总体中位 1,885.1 ms | 严格阻断公共前缀的对照基线 |
| **显式缓存 (Explicit Cache)** | 6/6 条链首发创建、后续稳定复用 | **链中位节省 51.4%** | **链中位下降 41.0%** | **本实验中最稳定、最推荐生产采纳的策略** |
| **隐式缓存 (全量 6 条链)** | 2 条链首发即命中（受此前显式链预热） | 链中位节省 44.7% | 链中位下降 40.5% | 受执行顺序与残留状态影响，不宜作无偏估计 |
| **隐式缓存 (无串扰 4 条链)** | 首发未命中、后两次自动识别前缀 | 链中位节省 30.0% | 链中位下降 31.7% | 仅作敏感性参考：零改造可用，但省钱幅度低于显式 |

*注：等价输入成本依据阿里云百炼官方公开单价与 API 返回的 `prompt_tokens`、`cache_creation_input_tokens`、`cached_tokens` 严格折算，输出 Token 均单独全额计费。*

## 三、为什么测这个？长 Prompt 时代的四大工程现实问题

在 Agent 智能体、企业知识库（RAG）、多轮复杂代码调试等场景中，开发者往往需要反复发送超长的上下文——包括庞大的系统人设指令、API Schema 定义、企业规章、几十页合同或长代码文件。

“上下文缓存（Context Caching）”在各家云厂商的宣传中听起来是一项“必省无疑”的技术，但在实际工程落地上，架构师和开发者普遍面临四个具体疑问：

1. **隐式缓存到底靠不靠谱？** 不写代码自动识别前缀，真的能保证在每次连续对话中稳定命中吗？
2. **显式缓存第一次创建要多付 25% 的溢价，到底复用几次才能真正回本？** 如果只问两三句话就结束对话，会不会反而被反向反噬、多花冤枉钱？
3. **缓存省下的究竟是逻辑 Token、实际账单，还是端到端响应延迟？** 延迟下降的幅度跟 Token 减少的比例是对齐的吗？
4. **开了缓存之后，模型输出的内容会不会因为状态复用而产生漂移或错误？**

为了给出客观、可复现的答案，我没有凭感觉写 Demo，而是围绕 `qwen3.8-27b` 设计了一组严格受控的基准测试。

## 四、百炼 Context Cache 官方机制与计费规则

根据阿里云百炼平台官方文档，`qwen3.8-27b`（华北 2 / 北京）原生支持上下文缓存。其底层计费机制设计非常明确：

- **冷请求普通输入**：按标准单价 $100\%$ 计费；
- **隐式缓存**：系统自动识别公共前缀（需 $\ge 1024$ tokens），命中部分按标准输入单价的 **$20\%$** 计费（节省 80%），但厂商明确声明“命中具有不确定性”；
- **显式缓存**：开发者通过在消息中设置 `"cache_control": {"type": "ephemeral"}` 手动声明缓存边界。**创建缓存时按标准输入单价的 $125\%$ 计费（收取 25% 溢价）；但在 5 分钟有效期（TTL）内，后续命中的 Token 仅按标准单价的 $10\%$ 计费（节省 90%）**；
- **输出 Token**：无论是否使用缓存，模型生成的 completion tokens 始终按全额价格独立计费。

这套定价模型决定了：**显式缓存不是免费午餐，它是一笔“先加价投资、后深度打折”的经济账**。

## 五、实验设计与控制变量：三策略 × 三档位 × 双样本

实验固定使用百炼托管 API 上的 `qwen3.8-27b`，关闭思考模式（`enable_thinking=false`），固定 `temperature=0`，`max_tokens=128`，请求超时限制 90 秒，全过程严格单流串行，**关闭自动重试（每次 observation 只允许一次 HTTP 请求）**。

实验矩阵设计如下：

- **3 种策略条件**：
  - `A: Cold Control（冷请求基线）`：在长 Prompt 最前侧注入每次唯一、等长的动态随机 Nonce，破坏公共前缀识别，强制服务端全量计算，用于获取对标基线；
  - `B: Implicit（隐式缓存）`：不传入任何缓存控制参数，整条链的前缀文本完全一致，测试云端自适应识别；
  - `C: Explicit（显式缓存）`：长前缀文本与 B 严格一致，在文档尾部显式声明 `cache_control: {"type": "ephemeral"}`。
- **3 个长 Prompt 档位**：`L1（约 2K tokens）`、`L2（约 6K tokens）`、`L3（约 10K tokens）`，跨越从起步门槛到典型长文档区间。
- **2 套独立合成台账样本**：`doc1` 与 `doc2`，完全由程序合成的虚构台账，排除互联网与预训练集污染。
- **每条缓存链连续 3 次请求**：
  - `pos=1`：首发请求（测试冷启动 / 显式创建开销）；
  - `pos=2`：第 1 次复用请求；
  - `pos=3`：第 2 次复用请求。

总 observation 计算：$3 \text{ 策略} \times 3 \text{ 长度档位} \times 2 \text{ 独立样本} \times 3 \text{ 链内请求} = \mathbf{54 \text{ 次正式调用}}$。  
18 条独立链在测试前使用随机种子 `seed=20260906` 预先完全随机化并打乱执行顺序，但每条链内部的 3 次请求保持紧凑连续，以保证在 5 分钟 TTL 窗口内完成。

## 六、确定性机器评分体系：告别 LLM-as-judge，只看绝对真值

为了彻底避免第一篇评测中可能遇到的“评分器覆盖不足”或“LLM-as-judge 主观偏差”，本次实验在任务定义上做了纯粹的工程简化：

每道题均为确定性台账字段检索，强制模型返回标准单行 JSON：
```json
{"answer": "<精确目标值>", "evidence_id": "<唯一记录ID>"}
```
评分程序通过本地 Python 函数严格对比 Ground Truth 字符串和唯一的关联证据编号。本次 54 次正式请求中，**机器验收通过率为 54/54（100%）**。这证明了：**缓存机制纯粹在 KV 前缀计算层面优化，并没有对 Qwen3.8-27B 的确定性抽取精度产生任何负面损害。**

## 七、Smoke 门禁与真实校准：在调用前修正 Prompt 规模的透明过程

在正式运行前，我严格按照预注册规范执行了 6 次 live smoke 预检。这一次预检不仅没有走过场，反而立了大功：

最初离线按字符数估算的合成文档偏大，smoke 阶段百炼服务端返回的实际 `prompt_tokens` 分别达到了 3,163、9,409 和 15,654 tokens，明显超出了原定的 2K/6K/10K 目标区间。  
我没有掩盖这个偏差，而是：
1. 原样保留这 6 次失败的 smoke 日志并归档；
2. 利用服务端实测的线性斜率，将记录行数从 40/125/210 严格校准为 24/79/133；
3. 建立 `PREREGISTRATION_V2.0_AMENDMENT.md`，重新冻结并生成执行清单与 SHA-256，再开启正式调用。

校准后正式 54 次调用的各档 Prompt 规模中位数分别为：**L1=1,986、L2=6,025.5、L3=9,987.5 tokens**，与目标极其贴合。

![缓存覆盖率](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig01_cache_coverage_cn.png)

实测数据表明：
- **显式缓存（Explicit）在 6 条链中表现出了绝对的规律性**：首个请求（pos=1）的 `cached_tokens` 均为 0，并准确返回了 `cache_creation_input_tokens`；而在随后的 pos=2 和 pos=3 请求中，缓存全部精准命中。

- **冷请求基线（Cold Control）**：18 次请求的 `cached_tokens` 均为 0，证明前置动态 Nonce 完美阻断了公共前缀，基线数据真实可靠。

## 九、结果二：延迟阶梯实测——从 3.0 秒到 0.8 秒的加速与长尾噪声

> 📌 **【此处上传并插入：图 2 响应延迟 (fig02_latency_cn.png)】**
![响应延迟](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig02_latency_cn.png)

延迟方面的数据展现了清晰的工程收益：

| Prompt 规模 | 冷请求平均延迟 | 显式第 1 次 (创建缓存) | 显式第 2 次 (首次命中) | 显式第 3 次 (二次命中) | 复用请求降幅 (vs 冷请求) |
|---|---:|---:|---:|---:|---:|
| **L1 (~2K tokens)** | 1,110.6 ms | 843.0 ms | 780.8 ms | 771.3 ms | **降 30.5%** |
| **L2 (~6K tokens)** | 1,920.5 ms | 1,412.3 ms | 733.2 ms | 775.9 ms | **降 61.8%** |
| **L3 (~10K tokens)** | 2,974.6 ms | 1,978.9 ms | 972.9 ms | 836.8 ms | **降 71.9%** |

核心观察：
1. **输入越长，缓存带来的延迟收益越震撼**：在 10K 档位下，冷请求需要耗费接近 3 秒（2,974 ms），而一旦命中缓存，后两次调用的耗时直接被压到了 **1 秒以内（836 ~ 972 ms）**，提速达到 3 倍以上！
2. **长尾噪声依然客观存在**：虽然中位数大幅缩减，但在百炼多租户云端环境下，冷请求 P95 达到了 3,121 ms，显式缓存 P95 也有 1,979 ms（受首次创建请求拖累）。缓存极大压缩了 Prefill 算力开销，但不能完全消除网络抖动与服务端排队波动。

## 十、结果三：成本模型与 ROI 推导——到底复用几次才真正回本？

> 📌 **【此处上传并插入：图 3 等价输入成本 (fig03_cost_cn.png)】**
![等价输入成本](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig03_cost_cn.png)

很多人担心显式缓存“创建要多收 25% 溢价，会不会亏本”。这里给出一个严密的数学公式与推演：

设稳定公共前缀长度为 $L$，普通输入基础单价为 $P$：
- **不使用缓存，调用 $N$ 次的累计成本**：
  $$C_{\text{cold}}(N) = N \cdot L \cdot P$$
- **使用显式缓存（第 1 次创建溢价 125%，后 $N-1$ 次按 10% 计费）的累计成本**：
  $$C_{\text{explicit}}(N) = 1.25 L \cdot P + (N - 1) \cdot 0.10 L \cdot P = (1.15 + 0.10 N) \cdot L \cdot P$$
- **盈亏平衡临界点计算**：
  $$C_{\text{explicit}}(N) \le C_{\text{cold}}(N) \implies 1.15 + 0.10 N \le N \implies 0.90 N \ge 1.15 \implies \mathbf{N \ge 1.278}$$

**ROI 推演结论极其明确**：
1. **$N=1$（单次提问）**：成本为冷请求的 $1.25$ 倍，**净亏 25%**（单次任务坚决不要加显式缓存标记）；
2. **$N=2$（仅需复用 1 次）**：显式成本为 $1.35 L P$，冷请求为 $2.0 L P$，**立即净省 32.5%**！
3. **$N=3$（复用 2 次，即本实验场景）**：显式成本为 $1.45 L P$，冷请求为 $3.0 L P$，理论节省 **51.7%** —— 这与我们在 54 次实测中得到的 **51.4% 中位净节省** 完美契合！
4. **$N=10$（多轮 Agent 或常驻客服）**：显式成本为 $2.15 L P$，冷请求为 $10.0 L P$，**净省 78.5%**，接近官方 10% 的理论极限。

## 十一、深度排障复盘：还原 L2-d2 与 L3-d2 隐式缓存被意外预热的时间线

> 📌 **【此处上传并插入：图 4 执行顺序审计热图 (fig04_execution_heatmap_cn.png)】**
![执行顺序审计](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig04_execution_heatmap_cn.png)

正如第一篇评测深度复盘 C5 任务一样，本次实验最值得深挖的一个技术现场，是**隐式缓存出现的两次“异常命中”**。

在 18 条链的随机执行日志中，我们观察到两条诡异记录：
- `execution_index=49` (implicit, L2, doc2, pos=1)：首发请求居然直接爆出了 `cached_tokens = 4992`！
- `execution_index=52` (implicit, L3, doc2, pos=1)：首发请求同样爆出了 `cached_tokens = 8320`！

调取完整时间戳日志复盘真相：
```text
[05:40:36 UTC] index=34: explicit, L2, doc2 (pos=1) -> 创建 L2-doc2 显式缓存
[05:40:39 UTC] index=36: explicit, L2, doc2 (pos=3) -> 完成显式链调用
... 仅过了 12 秒 ...
[05:40:51 UTC] index=49: implicit, L2, doc2 (pos=1) -> 发起首个隐式请求，直接命中 4992 tokens！

[05:39:49 UTC] index=4: explicit, L3, doc2 (pos=1) -> 创建 L3-doc2 显式缓存
... 仅过了 64 秒（远在 5 分钟 TTL 内部）...
[05:40:53 UTC] index=52: implicit, L3, doc2 (pos=1) -> 发起首个隐式请求，直接命中 8320 tokens！
```

**这一现象直接揭示了百炼云端底层的缓存架构特性**：  
同一主账号下、相同模型、相同前缀文本在显式缓存创建后，其前缀索引在物理集群中处于高活状态；随后的隐式请求无需带有任何标记，也能直接借道命中该公共前缀。  
**生产警示**：开发者如果在测试环境做基准压测，**仅仅把执行顺序随机打乱是不够的**！如果跨条件共用了相同的前缀文本，必须在各条件之间插入独立的 Namespace 前缀，或者等待 5 分钟以上的 TTL 冷却窗口（Washout Period），否则必将发生状态串扰。

## 十二、敏感性分析：排除串扰后的无污染子集表现

我们没有因出现串扰而删改或补跑数据，而是坚持预注册原则，将全部 54 条调用全量入库。

同时，我们进行了事后（post-hoc）敏感性切片：将那 2 条受串扰的隐式链剥离，仅保留 **4 条严格无污染的隐式链**（首请求 cached=0，后两次自动命中）进行纯净统计：
- **无串扰隐式链的等价输入成本中位节省**：**30.0%**（全量统计为 44.7%）；
- **无串扰隐式链的端到端延迟中位下降**：**31.7%**（全量统计为 40.5%）。

这一修正对比说明：**隐式缓存确实能在零改动下为开发者省下约 30% 的成本与延迟，但由于其折扣力度（20%单价）弱于显式缓存（10%单价），其综合收益依然显著低于显式缓存的 51.4%**。

## 十三、开发者工程落地指南：生产中如何设计 Prompt 布局与缓存边界

结合本次 60 次实测与官方规范，我为使用 Qwen3.8-27B 开展长文本与 Agent 架构设计的同学总结了四条落地铁律：

1. **三段式 Prompt 分层排布法**：
   - **第一层：全局规范与固定人设（不常变动，>1K tokens）** $\to$ **结尾处放置 `cache_control`**；
   - **第二层：检索引用的参考文档 / 代码库快照（同轮会话不变）** $\to$ **结尾处放置第 2 个 `cache_control`**；
   - **第三层：用户即时 Query 与动态对话历史（每轮变化）** $\to$ **严禁放置任何缓存标记**。
2. **评估对话轮次，按需启用显式缓存**：
   - 评估你的业务场景单会话平均交互轮数：若 $N \ge 2$，果断在长提示末端配置显式缓存；若属于一次性离线质检或单轮问答（$N=1$），坚决不要开启，避免白付 25% 溢价。
3. **警惕 5 分钟 TTL 窗口重置**：
   - 百炼托管缓存的生命周期通常为 5 分钟。交互型产品只要用户在 5 分钟内持续发起追问，缓存有效期会自动向后顺延；但若用户停顿超过 5 分钟，下一次请求将重新全额计算 Prefill。
4. **日志埋点务必区分物理 Token 与计费 Token**：
   - 监控看板不能只看 `prompt_tokens`！必须采集 `cache_creation_input_tokens` 与 `cached_tokens`，否则财务对账时会无法解释实际开销与账面 Token 的巨大差异。

## 十四、局限性说明与完整复现指引

为了保证科研与工程严谨性，明确本实验的边界条件：
1. **样本多样性有限**：本次采用 2 套完全合成的台账文档，不能覆盖代码、多模态、弱结构化文本等全部现实形态；
2. **观测样本规模**：正式实验为 54 次调用（18 条缓存链），旨在验证工程机制与可复现效应，不作全域宏观统计外推；
3. **延迟受时段影响**：延迟数据真实反映了评测时段内华北 2 地域的百炼线上表现，不同网络条件与不同时刻负载可能存在方差；
4. **成本基于公开单价核算**：金额为理论等价折算，开发者账户的实际扣费还需视具体的优惠套餐、抵扣包或免费额度而定。
