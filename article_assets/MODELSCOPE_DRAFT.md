# 【性能测试】Qwen3.8-27B 长 Prompt 缓存值不值得用？60 次真实调用实测命中、延迟与 Token 成本

> 本文包含 6 次 pilot 预检和 54 次正式调用。所有请求均真实调用阿里云百炼华北 2（北京）的 `qwen3.8-27b` 模型；原始逐条记录、预注册设计、固定随机执行顺序、确定性评分器、分析脚本及 SHA-256 校验清单已全部开源：  
> GitHub 仓库：https://github.com/Sam-Hui-dot/qwen38-context-cache-benchmark

---

## 一、先给结论：显式缓存复用覆盖率 99.2%，综合输入成本节省 51.4%

在本实验的连续三次请求链中，**显式缓存（Explicit Cache）表现出高度的确定性与稳定性**：6/6 条链均呈现“首请求创建缓存、后两次稳定命中”，复用请求的缓存 Token 覆盖率达到 **98.49% ~ 99.70%（平均 99.2%）**，命中率达到 12/12（100%）。按百炼官方价格权重折算，三次请求链的总等价输入成本约为匹配冷请求的 **48.6%**（即中位净节省 **51.4%**）。而在端到端响应耗时上，显式缓存三请求链观察到的链总延迟中位数下降为 **41.0%**。

**隐式缓存（Implicit Cache）虽然无需任何客户端参数改造，但行为存在显著的不确定性**。更重要的是，本次严密的随机执行顺序暴露了一个极其关键的实验设计问题：不仅存在显式请求对后续隐式请求的预热残留，反方向上也观察到了隐式请求可能缩短显式首发创建延迟的迹象。本文完整保留全部 54 条原始数据，并将“排除串扰后的 4 条隐式链”单独作为事后（post-hoc）敏感性分析呈现；同时将 41.0% 延迟降幅明确界定为描述性观测结果，而非严格隔离下的纯因果估计。

## 二、结果速览表：三类策略全景横评

| 策略条件 | 缓存生效行为 | 3次请求等价输入成本 | 链总响应延迟 | 应如何客观解读 |
|---|---|---:|---:|---|
| **冷请求基线 (Cold Control)** | 18 次请求 `cached_tokens` 恒为 0 | 100% (基线) | 总体中位 1,885.1 ms | 严格阻断公共前缀的对标对照组 |
| **显式缓存 (Explicit Cache)** | 6/6 条链首发创建、后续稳定复用 | **链中位节省 51.4%** | **链中位下降 41.0%** | **本实验中最稳定、工程落地最可控的策略** |
| **隐式缓存 (全量 6 条链)** | 2 条链首发即命中（受此前显式链预热） | 链中位节省 41.9% | 链中位下降 38.1% | 受执行顺序与残留状态影响，不宜作无偏估计 |
| **隐式缓存 (无串扰 4 条链)** | 首发未命中、后两次自动识别前缀 | 链中位节省 30.0% | 链中位下降 31.7% | 仅作事后敏感性参考：零改造可用，但降本幅度低于显式 |

*注：等价输入成本依据阿里云百炼官方公开单价与 API 返回的 `prompt_tokens`、`cache_creation_input_tokens`、`cached_tokens` 严格折算，输出 Token 均单独全额计费。*

## 三、为什么测这个？长 Prompt 时代的四大工程现实问题

在 Agent 智能体、企业知识库（RAG）、多轮复杂代码调试等场景中，开发者往往需要反复发送超长的上下文——包括庞大的系统人设指令、API Schema 定义、企业规章、长文档或代码文件。

“上下文缓存（Context Caching）”在各大云厂商的模型服务中都是主推特性，但在工程选型上，开发者通常面临四个具体疑问：

1. **隐式缓存是否足够稳定？** 不写额外参数让系统自动识别前缀，在生产多轮调用中能有多大把握命中？
2. **显式缓存首次创建要多付 25% 溢价，到底复用几次才能回本？** 如果会话轮数较短，会不会反而增加调用成本？
3. **缓存省下的究竟是逻辑 Token、实际费用，还是响应延迟？** 延迟下降的幅度是否与 Token 比例严格对齐？
4. **启用缓存后，模型输出的内容是否会因为 KV 状态复用而产生漂移或质量退化？**

为了给出可复现、有数据依据的工程参考，我围绕百炼平台托管的 `qwen3.8-27b` 设计了一组受控基准测试。

## 四、百炼 Context Cache 官方机制与计费规则

根据阿里云百炼平台官方文档，`qwen3.8-27b`（华北 2 / 北京）原生支持上下文缓存。其底层计费机制设计如下：

- **冷请求普通输入**：按标准单价 $100\%$ 计费（当前刊例价 ¥3/M tokens）；
- **隐式缓存**：系统自动识别公共前缀（需 $\ge 1024$ tokens），命中部分按标准输入单价的 **$20\%$** 计费（当前刊例价 ¥0.6/M tokens，节省 80%），但官方明确指出隐式缓存的生命周期由系统自行管理，存活时间具有不确定性；
- **显式缓存**：开发者在消息体中通过 `"cache_control": {"type": "ephemeral"}` 显式声明缓存边界。**创建缓存时按标准输入单价的 $125\%$ 计费（¥3.75/M tokens，收取 25% 溢价）；而在 5 分钟有效期（TTL）内，后续命中的 Token 仅按标准单价的 $10\%$ 计费（¥0.3/M tokens，节省 90%）**，每次命中会自动将该显式缓存块的 5 分钟有效期重新计时；
- **输出 Token**：无论是否使用缓存，模型生成的 completion tokens 始终按全额价格（¥12/M tokens）独立计费。

这套定价模型决定了：**显式缓存不是单纯的免费加速，而是一笔“前期溢价创建、后续深度折扣”的经济账**。

## 五、实验设计与控制变量：三策略 × 三档位 × 双样本

实验固定使用百炼托管 API 上的 `qwen3.8-27b`，关闭思考模式（`enable_thinking=false`），固定 `temperature=0`，`max_tokens=128`，请求超时限制 90 秒，全过程严格单流串行，**关闭自动重试（每次 observation 只允许一次 HTTP 请求）**。

实验矩阵设计如下：

- **3 种策略条件**：
  - `A: Cold Control（冷请求基线）`：在长 Prompt 最前侧注入每次唯一、等长的动态随机 Nonce，破坏公共前缀识别，强制服务端进行全量 Prefill 计算，用于获取对标基线；
  - `B: Implicit（隐式缓存）`：不传入任何缓存控制参数，整条链的长前缀文本完全一致，观察云端自适应识别效果；
  - `C: Explicit（显式缓存）`：长前缀文本与 B 严格一致，在文档尾部显式声明 `cache_control: {"type": "ephemeral"}`。
- **3 个长 Prompt 档位**：`L1（约 2K tokens）`、`L2（约 6K tokens）`、`L3（约 10K tokens）`，覆盖从起步门槛到典型长文档区间。
- **2 套独立合成台账样本**：`doc1` 与 `doc2`，完全由程序合成的虚构台账数据，排除互联网与训练集记忆干扰。
- **每条缓存链连续 3 次请求**：
  - `pos=1`：首发请求（测试冷启动 / 显式创建开销）；
  - `pos=2`：第 1 次复用请求；
  - `pos=3`：第 2 次复用请求。

总 observation 计算：$3 \text{ 策略} \times 3 \text{ 长度档位} \times 2 \text{ 独立样本} \times 3 \text{ 链内请求} = \mathbf{54 \text{ 次正式调用}}$。  
18 条独立链在测试前使用随机种子 `seed=20260906` 预先完全随机化并打乱执行顺序，但每条链内部的 3 次请求保持紧凑连续执行。

## 六、确定性机器评分体系：告别 LLM-as-judge，只看绝对真值

为了避免评测中可能出现的“评分器逻辑模糊”或“LLM-as-judge 主观打分漂移”，本次实验在任务定义上做了严格的工程收敛：

每道题均为确定性台账字段检索，强制模型返回标准单行 JSON：
```json
{"answer": "<精确目标值>", "evidence_id": "<唯一记录ID>"}
```
评分程序通过本地 Python 函数严格比对预先计算好的 Ground Truth 字符串和唯一的关联证据编号。

本次 54 次正式请求中，**机器验收通过率为 54/54（100%）**。这表明：**在本实验所测试的确定性台账抽取任务中，54 次请求未观察到由缓存引起的准确率下降**。这能够证明缓存状态未破坏本组检索的答案一致性，但并不外推为模型在所有复杂生成任务中均完全不受影响。

## 七、Smoke 门禁与真实校准：在调用前修正 Prompt 规模的透明过程

在正式运行前，我严格按照预注册规范执行了 6 次 live smoke 预检。这一次预检有效拦截了离线设计与真实服务端的偏差：

最初离线按字符数估算的合成文档偏大，smoke 阶段百炼服务端返回的实际 `prompt_tokens` 分别达到了 3,163、9,409 和 15,654 tokens，超出了原定的 2K/6K/10K 目标区间。  
我没有掩盖这个偏差，而是：
1. 原样保留这 6 次超出区间的 smoke 记录并归档；
2. 利用服务端实测的斜率，将记录行数从 40/125/210 校准为 24/79/133；
3. 建立 `PREREGISTRATION_V2.0_AMENDMENT.md`，重新冻结并生成执行清单与 SHA-256，再开启正式调用。

校准后正式 54 次调用的各档 Prompt 规模中位数分别为：**L1=1,986、L2=6,025.5、L3=9,987.5 tokens**，符合预设档位。

## 八、结果一：显式缓存的复用覆盖率与稳定性实测

> 📌 **【此处上传并插入：图 1 缓存覆盖率 (fig01_cache_coverage_cn.png)】**
![缓存覆盖率](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig01_cache_coverage_cn.png)

实测数据表明：
- **显式缓存（Explicit）在 6 条链中表现出了清晰的确定性**：首个请求（pos=1）的 `cached_tokens` 均为 0，并准确返回了 `cache_creation_input_tokens`；而在随后的 pos=2 和 pos=3 请求中，缓存 12/12 全部命中（Hit Rate 100%）。
- 在 L1、L2、L3 三档下，复用请求的 `cached_tokens` 实际命中范围分别为 **1,956 ~ 1,959**、**5,995 ~ 5,999** 和 **9,951 ~ 9,968** tokens，**缓存 Token 覆盖率稳定在 98.49% ~ 99.70%（平均 99.2%）**。除了末尾变动的微小 Query 差异外，其余稳定前缀均被完整复用。
- **冷请求基线（Cold Control）**：18 次请求的 `cached_tokens` 均为 0，证明前置动态 Nonce 达到了阻断公共前缀的预期。

## 九、结果二：延迟阶梯实测——从 3.0 秒到 0.8 秒的加速表现

> 📌 **【此处上传并插入：图 2 不同长前缀下缓存复用请求的端到端延迟 (fig02_latency_cn.png)】**
![响应延迟](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig02_latency_cn.png)

在端到端耗时方面，统一以表格中的平均延迟口径计算（复用请求取 pos2 与 pos3 平均耗时），对比冷请求平均延迟：

| Prompt 规模 | 冷请求平均延迟 | 显式第 1 次 (创建缓存) | 显式第 2 次 (首次命中) | 显式第 3 次 (二次命中) | 复用请求平均降幅 (vs 冷请求) |
|---|---:|---:|---:|---:|---:|
| **L1 (~2K tokens)** | 1,110.6 ms | 843.0 ms | 780.8 ms | 771.3 ms | **下降 30.1%** |
| **L2 (~6K tokens)** | 1,920.5 ms | 1,412.3 ms | 733.2 ms | 775.9 ms | **下降 60.7%** |
| **L3 (~10K tokens)** | 2,974.6 ms | 1,978.9 ms | 972.9 ms | 836.8 ms | **下降 69.6%** |

核心观察：
1. **长前缀下复用请求提速明显**：在 10K 档位下，冷请求平均耗时近 3 秒（2,974.6 ms），而一旦命中缓存，后两次调用的耗时回落至 **1 秒以内（836.8 ~ 972.9 ms）**，复用请求平均延迟降幅达到近 70%；
2. **需理性看待延迟指标的因果性**：在本次执行顺序下，显式缓存三请求链观察到的链总延迟中位下降为 41.0%。但需要特别指出的是，由于后文排查发现部分匹配的隐式链先于显式链执行，该延迟指标可能受到跨条件预热的伴随影响，因此建议视为本次特定执行排期下的描述性统计，而不宜直接作为严格隔离的纯因果估计；
3. **长尾与排队波动仍在**：在云端多租户环境下，虽然中位延迟大幅下降，但网络抖动与后端调度仍会形成长尾分布，缓存优化的是 Prefill 阶段的计算开销，并不消除网络传输与排队时间。

## 十、结果三：成本模型与 ROI 推导——到底复用几次才真正回本？

> 📌 **【此处上传并插入：图 3 等价输入成本 (fig03_cost_cn.png)】**
![等价输入成本](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig03_cost_cn.png)

显式缓存虽然有单价 10% 的深度折扣，但首次创建需要多收 25% 溢价。这里给出严密的成本函数与回本周期推导：

设稳定公共前缀长度为 $L$，普通输入基础单价为 $P$：
- **不使用缓存，调用 $N$ 次的累计成本**：
  $$C_{\text{cold}}(N) = N \cdot L \cdot P$$
- **使用显式缓存（第 1 次创建溢价 125%，后 $N-1$ 次按 10% 计费）的累计成本**：
  $$C_{\text{explicit}}(N) = 1.25 L \cdot P + (N - 1) \cdot 0.10 L \cdot P = (1.15 + 0.10 N) \cdot L \cdot P$$
- **盈亏平衡临界点计算**：
  $$C_{\text{explicit}}(N) \le C_{\text{cold}}(N) \implies 1.15 + 0.10 N \le N \implies 0.90 N \ge 1.15 \implies \mathbf{N \ge 1.278}$$

**ROI 推演结论**：
1. **$N=1$（单次提问）**：成本为冷请求的 $1.25$ 倍，**净亏 25%**（单次调用场景坚决不要开启显式缓存）；
2. **$N=2$（仅需复用 1 次）**：显式成本为 $1.35 L P$，冷请求为 $2.0 L P$，**即可净省 32.5%**；
3. **$N=3$（复用 2 次，即本实验场景）**：显式成本为 $1.45 L P$，冷请求为 $3.0 L P$，理论节省 **51.7%** —— 这与我们在 54 次实测中得到的 **51.4% 中位净节省** 高度一致；
4. **$N=10$（长期复用）**：显式成本为 $2.15 L P$，冷请求为 $10.0 L P$，**净省 78.5%**，逼近 90% 的理论折扣极限。

## 十一、深度排障复盘：还原 L2-d2 与 L3-d2 隐式缓存被意外预热的时间线

> 📌 **【此处上传并插入：图 4 执行顺序审计热图 (fig04_execution_heatmap_cn.png)】**
![执行顺序审计](https://raw.githubusercontent.com/Sam-Hui-dot/qwen38-context-cache-benchmark/main/article_assets/fig04_execution_heatmap_cn.png)

本次实验最值得公开复盘的一个技术现场，是**隐式缓存出现的两次“异常提早命中”**。

在 18 条链的随机执行日志中，我们观察到两条非预期记录：
- `execution_index=49` (implicit, L2, doc2, pos=1)：首发请求返回了 `cached_tokens = 4992`；
- `execution_index=52` (implicit, L3, doc2, pos=1)：首发请求返回了 `cached_tokens = 8320`。

调取精确时间戳日志还原现场：
```text
[05:40:36 UTC] index=34: explicit, L2, doc2 (pos=1) -> 创建 L2-doc2 显式缓存
[05:40:39 UTC] index=36: explicit, L2, doc2 (pos=3) -> 完成显式链调用
... 仅相隔 12 秒 ...
[05:40:51 UTC] index=49: implicit, L2, doc2 (pos=1) -> 发起首个隐式请求，命中 4992 tokens！

[05:39:49 UTC] index=4: explicit, L3, doc2 (pos=1) -> 创建 L3-doc2 显式缓存
... 相隔 64 秒 ...
[05:40:53 UTC] index=52: implicit, L3, doc2 (pos=1) -> 发起首个隐式请求，命中 8320 tokens！
```

与此同时，反向关系同样值得关注：L3-doc1 与 L2-doc1 则是 implicit 链先于 explicit 链执行，随后的显式首次创建耗时（L3-doc1 仅 846 ms，L2-doc1 仅 770 ms）明显低于冷请求首发的 2.6 ~ 3.1 秒，显示其物理前缀计算同样可能受过前置请求的影响。

**客观推断与排障结论**：  
这一现象与跨条件缓存状态残留的解释高度一致，但现有实验数据无法进一步判断显式缓存与隐式缓存是否共享底层存储架构，也不能据此推断百炼内部的具体实现机制。要彻底验证两者的存储边界，需要专门设计带有隔离 Namespace 与严格等待机制的跟进实验。  
**工程警示**：开发者如果在测试环境进行缓存性能对比，**单纯依靠随机打乱请求顺序是不够的**。如果测试跨条件复用了完全一致的前缀，必须为每个测试组注入独立命名空间，或者留出充分的时间间隔，否则极易发生状态穿透。

## 十二、敏感性分析：排除串扰后的无污染子集表现

坚持预注册原则，我们没有因出现串扰而删改或重跑任何数据，全部 54 条调用原样保留归档。

同时，我们进行了事后（post-hoc）敏感性切片：剥离受影响的 2 条隐式链，仅对 **4 条严格无污染的隐式链**（首请求 cached=0，后两次自动命中）进行测算：
- **全量 6 条隐式链的指标中位数**：等价输入成本中位节省 **41.9%**，链总延迟中位下降 **38.1%**；
- **无串扰 4 条隐式链的指标中位数**：等价输入成本中位节省 **30.0%**，链总延迟中位下降 **31.7%**。

对比可见：排除残留预热后，隐式缓存依然能在免客户端改造的前提下为开发者节约约 $30\%$ 的成本与延迟；但因为其单价折扣为 20%（显式为 10%），其综合降本幅度仍显著低于显式缓存的 51.4%。

## 十三、开发者工程落地指南：生产中如何设计 Prompt 布局与缓存边界

结合本次 60 次实测与官方技术规范，为使用 Qwen3.8-27B 开展长文本、RAG 与 Agent 开发的团队总结三条设计原则：

1. **三段式 Prompt 布局与显式边界划分**：
   - **头部固定区（系统人设、格式规范、输出契约，>1K tokens）** $\to$ **结尾显式配置 `cache_control`**；
   - **中部半稳定区（当次会话引用的文档、代码片段、上下文知识库）** $\to$ **结尾配置第 2 个 `cache_control`**；
   - **尾部动态区（用户即时 Query、变动消息历史）** $\to$ **不设置任何缓存标记**。
2. **依据交互轮数决定是否开启显式标记**：
   - 评估业务场景的单会话平均轮次：若 $N \ge 2$，建议在长前缀末尾显式配置缓存标记以锁定 90% 深度折扣；若属于单次检索或单轮任务（$N=1$），不要添加显式标记，避免承担 25% 的无谓溢价。
3. **正确理解 TTL 机制与实验隔离**：
   - 百炼文档明确指出，**显式缓存**具备 5 分钟的基础有效期（每次命中重新计时），而**隐式缓存**的生命周期由系统动态维护，具有不确定性。在做系统压测或多租户隔离设计时，防范缓存穿透最稳妥的手段是加入租户隔离前缀，而非单纯依赖时间等待。

## 十四、局限性说明与完整复现指引

明确本实验的边界条件与方法学局限：
1. **样本多样性有限**：测试采用 2 套完全合成的台账文本，未覆盖复杂代码库、多模态或自由对话等真实语料形态；
2. **样本规模定位**：正式实验包含 54 次调用（18 条缓存链），旨在提供清晰的工程机制对照与可复现基准，不作大规模统计外推；
3. **延迟指标的描述性**：延迟数据反映了评测时段内华北 2 地域的百炼公有云表现，受网络与服务端排队影响，且部分链延迟可能受跨条件预热影响，应作为描述性观测参考；
4. **成本基于公开计费模型折算**：金额依据官方公布单价折算等价输入量，开发者账单实际支出还取决于账户的具体套餐与免费额度。
